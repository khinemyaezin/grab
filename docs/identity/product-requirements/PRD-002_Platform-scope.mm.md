# အသုံးပြုနေတဲ့ App နဲ့ လုပ်ငန်းအလိုက် ဝင်ရောက်ခွင့်

## ၁။ အကျဉ်းချုပ်

ဒီ PRD က အသုံးပြုသူတစ်ယောက်ကို လက်ရှိသုံးနေတဲ့ App နဲ့ လုပ်ကိုင်နေတဲ့
လုပ်ငန်းအလိုက် ဘယ်လိုဝင်ရောက်ခွင့်ပေးမလဲဆိုတာ သတ်မှတ်ထားပါတယ်။
အသုံးပြုသူတစ်ယောက်က အကောင့်တစ်ခုတည်းနဲ့ Customer App၊ Seller Portal နဲ့
Admin Console တို့ကို လုံခြုံစွာ အသုံးပြုနိုင်ရပါမယ်။ သူ့လုပ်ပိုင်ခွင့်က
လက်ရှိသုံးနေတဲ့ App အပြင် လက်ရှိစီမံနေတဲ့ ရောင်းချသူလုပ်ငန်း (`Merchant`)၊
အွန်လိုင်းဆိုင်မျက်နှာစာ (`Storefront`) သို့မဟုတ် ပစ္စည်းသိုလှောင်/ပို့ဆောင်ရာ
နေရာ (`Fulfillment Location`) အပေါ်လည်း မူတည်ရပါမယ်။

အဓိကသဘောတရားက အကောင့်တစ်ခုတည်းနဲ့ စနစ်ဝင်နိုင်ပေမယ့် လုပ်ပိုင်ခွင့်ကိုတော့
လက်ရှိသုံးနေတဲ့ App နဲ့ ရွေးထားတဲ့ လုပ်ငန်းနယ်ပယ် (`context`) အလိုက်
တစ်ကြိမ်ချင်း စစ်ဆေးရမယ်ဆိုတာ ဖြစ်ပါတယ်။

## ၂။ ဖြေရှင်းရမယ့်ပြဿနာ

`SELLER` လို နေရာတိုင်းမှာ အကျိုးသက်ရောက်တဲ့ အခန်းကဏ္ဍ (`global role`)
တစ်ခုတည်းနဲ့ အသုံးပြုသူတစ်ယောက်က ဘယ် App မှာ၊ ဘယ်ရောင်းချသူလုပ်ငန်းအတွက်
အလုပ်လုပ်ခွင့်ရှိတယ်ဆိုတာ မပြောနိုင်ပါဘူး။ ဒီလိုသတ်မှတ်ထားရင် မသက်ဆိုင်တဲ့
ရောင်းချသူလုပ်ငန်းကိုပါ ဝင်ရောက်ခွင့်ရသွားနိုင်ပါတယ်။ ရောင်းချသူလုပ်ငန်း
တစ်ခုအတွက် လုပ်ပိုင်ခွင့်ကို ယာယီပိတ်လိုက်တဲ့အခါ အဲဒီအသုံးပြုသူရဲ့
Customer App ဝင်ရောက်ခွင့်ပါ မှားယွင်းပြီး ပိတ်သွားနိုင်ပါတယ်။

## ၃။ အသုံးပြုမယ့်သူတွေ

- Customer ဖြစ်ပြီး ရောင်းချသူလုပ်ငန်းတစ်ခုကို ကိုယ်တိုင်လုပ်ကိုင်သူ သို့မဟုတ်
  အဲဒီလုပ်ငန်းမှာ အလုပ်လုပ်သူ
- ရောင်းချသူလုပ်ငန်း လျှောက်ထားသူနဲ့ ပိုင်ရှင်
- ရောင်းချသူလုပ်ငန်း စီမံခန့်ခွဲသူနဲ့ အွန်လိုင်းဆိုင်ဝန်ထမ်း
- ကုန်ပစ္စည်းစာရင်း၊ ကုန်လက်ကျန်နဲ့ အော်ဒါတွေကို စီမံသူ
- Platform စီမံခန့်ခွဲသူနဲ့ ရောင်းချသူလုပ်ငန်း အတည်ပြုစစ်ဆေးသူ

## ၄။ ရည်ရွယ်ချက်များ

- အီးမေးလ်အကောင့်တစ်ခုတည်းနဲ့ ခွင့်ပြုထားတဲ့ App အားလုံးကို
  အသုံးပြုနိုင်စေပြီး အသုံးပြုသူအကောင့် ထပ်ဖန်တီးစရာမလိုအောင် လုပ်ရန်
- အသုံးပြုသူက တစ်ကြိမ်စနစ်ဝင်ထားသော်လည်း ဝင်ရောက်ခွင့်ကို လက်ရှိသုံးနေတဲ့
  App နဲ့ ရွေးထားတဲ့ လုပ်ငန်းနယ်ပယ်အလိုက် အမြဲစစ်ဆေးရန်
- ရောင်းချသူလုပ်ငန်းအများအပြားကို စီမံသူအတွက် လုံခြုံတဲ့ လုပ်ငန်းနယ်ပယ်
  ရွေးချယ်မှုနဲ့ ရည်ရွယ်ချက်ရှိရှိ ပြောင်းနိုင်တဲ့လုပ်ဆောင်ချက် ပေးရန်

## ၅။ ဒီလုပ်ဆောင်ချက်ထဲမှာ ပါဝင်မယ့်အရာတွေ

- စနစ်က အသိအမှတ်ပြုထားတဲ့ App သတ်မှတ်ချက်များနဲ့ App တစ်ခုချင်းစီအတွက်
  သီးခြားအခန်းကဏ္ဍများ
- ရောင်းချသူလုပ်ငန်း၊ အွန်လိုင်းဆိုင်နဲ့ ပစ္စည်းသိုလှောင်/ပို့ဆောင်ရာနေရာ
  တစ်ခုချင်းစီအလိုက်
  ကန့်သတ်ထားတဲ့ ဝင်ရောက်ခွင့်သတ်မှတ်ချက်များ
- Seller Portal မှာ လက်ရှိလုပ်ငန်းနယ်ပယ်ကို ရွေးချယ်ခြင်းနဲ့ ပြောင်းခြင်း
- ရွေးထားတဲ့လုပ်ငန်းနယ်ပယ်နဲ့ ချိတ်ထားတဲ့ စနစ်ဝင်ခြင်း၊ session သက်တမ်းတိုးခြင်း၊
  စနစ်ထွက်ခြင်းနဲ့
  ဝင်ရောက်ခွင့်ပိတ်သိမ်းခြင်း
- ရောင်းချသူလုပ်ငန်းရဲ့ အခြေအနေပြောင်းလဲမှုအလိုက် ဖန်တီးလာမယ့်
  Merchant Applicant နဲ့ Merchant Owner ဝင်ရောက်ခွင့်
- ရောင်းချသူလုပ်ငန်းနဲ့ အွန်လိုင်းဆိုင်ဝန်ထမ်းတွေကို အီးမေးလ်နဲ့ ဖိတ်ခေါ်ခြင်း
- နယ်ပယ်ကန့်သတ်ထားတဲ့ ဝင်ရောက်ခွင့်တွေကို စီမံခန့်ခွဲသူက ကြည့်ရှုစီမံခြင်း
- ဝင်ရောက်ခွင့်ပေးခြင်း၊ ဖိတ်ခေါ်မှု၊ လုပ်ငန်းနယ်ပယ်ပြောင်းခြင်းနဲ့
  ဝင်ရောက်ခွင့်ငြင်းပယ်ခြင်းတို့အတွက် စစ်ဆေးမှတ်တမ်း (`audit log`) များ
- လက်ရှိ နေရာတိုင်းမှာအကျိုးသက်ရောက်နေတဲ့ Customer၊ Seller နဲ့ Admin
  အခန်းကဏ္ဍသတ်မှတ်ချက်တွေကို
  ပုံစံအသစ်ဆီ ပြောင်းရွှေ့ခြင်း

## ၆။ ဒီလုပ်ဆောင်ချက်ထဲမှာ မပါဝင်သေးတဲ့အရာတွေ

- ရောင်းချသူလုပ်ငန်းရဲ့ တရားဝင်အချက်အလက်၊ အတည်ပြုစည်းမျဉ်း၊ အခွန်အချက်အလက်၊
  လိပ်စာနဲ့ အွန်လိုင်းဆိုင်ပြင်ဆင်မှု။ ဒီအရာတွေကို Merchant module က
  တာဝန်ယူမယ်
- ကုန်ပစ္စည်း၊ ကုန်လက်ကျန်၊ အော်ဒါနဲ့ ငွေပေးချေမှုဆိုင်ရာ လုပ်ငန်းစည်းမျဉ်းများ
- တကယ့်လိပ်စာမရှိဘဲ ပစ္စည်းသိုလှောင်/ပို့ဆောင်ရာနေရာတစ်ခု ဖန်တီးခြင်း
- Social login၊ MFA၊ အီးမေးလ်အတည်ပြုခြင်းနဲ့ စကားဝှက်ပြန်လည်သတ်မှတ်ခြင်း
- သာမန်အသုံးပြုသူက လုပ်ပိုင်ခွင့်တွေကို စိတ်ကြိုက်ဖန်တီးပြင်ဆင်နိုင်တဲ့
  permission editor
- အသုံးပြုသူသုံး App က platform အသစ် သို့မဟုတ် လုပ်ပိုင်ခွင့်နယ်ပယ်အမျိုးအစား
  အသစ်ကို ကိုယ်တိုင်သတ်မှတ်နိုင်ခြင်း

## ၇။ အဓိကလုပ်ဆောင်ချက်များ

### ၇.၁။ အကောင့်တစ်ခုတည်းနဲ့ Platform အများအပြား အသုံးပြုခြင်း

ရောင်းချသူလုပ်ငန်းတစ်ခုမှာ အလုပ်လုပ်နေတဲ့ Customer က Customer App နဲ့
Seller Portal နှစ်ခုလုံးမှာ အကောင့်တစ်ခုတည်းကို သုံးနိုင်ရပါမယ်။
သီးခြားအကောင့်နဲ့ စကားဝှက် ထပ်မလိုရပါဘူး။

စနစ်က အောက်ပါအချက်တွေကို လုပ်ပေးရပါမယ် —

- အီးမေးလ်တစ်ခုစီအတွက် အသုံးပြုသူအကောင့်မှတ်တမ်းတစ်ခုတည်းသာ ထားရမယ်
- မှန်ကန်တဲ့ အီးမေးလ်နဲ့ စကားဝှက်တစ်စုံတည်းကိုသုံးပြီး ဝင်ရောက်ခွင့်ရှိတဲ့
  App အားလုံးမှာ အသုံးပြုသူကို စစ်ဆေးအတည်ပြုနိုင်ရမယ်
- စနစ်ဝင်ပြီးနောက် လက်ရှိသုံးနေတဲ့ App နဲ့ သက်ဆိုင်တဲ့ ဝင်ရောက်ခွင့်ကိုပဲ
  ဖတ်ယူရမယ်
- ဝင်ရောက်ခွင့်သတ်မှတ်ထားခြင်းမရှိတဲ့ App ကို ငြင်းပယ်ပြီး
  ဝင်ရောက်ခွင့်မရှိကြောင်း ရှင်းလင်းတဲ့စာသား ပြရမယ်
- Customer သို့မဟုတ် Seller အဖြစ် ကိုယ်တိုင်အကောင့်ဖွင့်ခြင်းကနေ
  Admin Console ဝင်ရောက်ခွင့် မရနိုင်အောင် ကာကွယ်ရမယ်

### ၇.၂။ လုံခြုံတဲ့ Context ရွေးချယ်မှု

လုပ်ငန်းအများအပြားကို စီမံတဲ့အသုံးပြုသူက လက်ရှိအလုပ်လုပ်မယ့်
ရောင်းချသူလုပ်ငန်း သို့မဟုတ် အွန်လိုင်းဆိုင်ကို ရွေးချယ်ရပါမယ်။ ဒါမှသာ
မှားယွင်းတဲ့လုပ်ငန်းရဲ့ အချက်အလက်ကို မတော်တဆ ပြင်ဆင်မိတာမျိုး မဖြစ်မှာပါ။

စနစ်က အောက်ပါအချက်တွေကို လုပ်ပေးရပါမယ် —

- အသုံးပြုသူမှာ အသက်ဝင်နေတဲ့ Seller Portal ဝင်ရောက်ခွင့်သတ်မှတ်ချက် မရှိရင်
  စီမံခန့်ခွဲခွင့် ငြင်းပယ်ရမယ်
- အသက်ဝင်နေတဲ့ လုပ်ငန်းနယ်ပယ်တစ်ခုတည်းရှိရင် အလိုအလျောက်ရွေးနိုင်ပြီး
  ရွေးထားတာကို ထင်ရှားစွာ ပြရမယ်
- အသက်ဝင်နေတဲ့ လုပ်ငန်းနယ်ပယ်တစ်ခုထက်ပိုရင် အသုံးပြုသူကိုယ်တိုင် ရွေးရမယ်။
  ရွေးချယ်ရာမှာ နည်းပညာသုံး ID ကို အဓိကမပြဘဲ လူသိနိုင်တဲ့ ရောင်းချသူလုပ်ငန်း
  သို့မဟုတ် အွန်လိုင်းဆိုင်အမည်ကို ပြရမယ်
- ရွေးလိုက်တဲ့ လုပ်ငန်းနယ်ပယ်က လက်ရှိအသုံးပြုသူနဲ့ App အတွက် အသက်ဝင်နေတဲ့
  ဝင်ရောက်ခွင့်သတ်မှတ်ချက်တစ်ခုနဲ့ အမှန်တကယ်သက်ဆိုင်ကြောင်း စစ်ဆေးရမယ်
- Seller Portal မှာ စနစ်ဝင်အသုံးပြုနေချိန်တစ်ခုအတွင်း တစ်ချိန်တည်း
  လုပ်ငန်းနယ်ပယ်တစ်ခုတည်းသာ အသက်ဝင်ရမယ်။ Session သက်တမ်းတိုးပြီးရင်လည်း
  အဲဒီလုပ်ငန်းနယ်ပယ်ကိုပဲ
  ဆက်ထိန်းထားရမယ်

### ၇.၃။ Context ကို ရည်ရွယ်ချက်ရှိရှိ ပြောင်းခြင်း

ရောင်းချသူလုပ်ငန်းအများအပြားကို စီမံတဲ့အသုံးပြုသူက လုပ်ငန်းတစ်ခုကနေ တစ်ခုကို
ရည်ရွယ်ချက်ရှိရှိ ပြောင်းနိုင်ရပါမယ်။ ပြောင်းပြီးနောက် လုပ်ဆောင်မှုအားလုံးက
အသစ်ရွေးထားတဲ့လုပ်ငန်းနဲ့ပဲ သက်ဆိုင်ရပါမယ်။

စနစ်က အောက်ပါအချက်တွေကို လုပ်ပေးရပါမယ် —

- အတည်ပြုပြီး အသက်ဝင်နေတဲ့ ဝင်ရောက်ခွင့်သတ်မှတ်ချက်တွေထဲက ရွေးနိုင်တဲ့
  အမည်ရှင်းလင်းတဲ့ လုပ်ငန်းပြောင်းရန်နေရာ (`context switcher`) ပေးရမယ်
- အသစ်ရွေးထားတဲ့ လုပ်ငန်းနယ်ပယ်နဲ့ session အသစ်ဖန်တီးပြီး နောက်ထပ်
  တောင်းဆိုမှုတွေအတွက် အဟောင်းကို ဆက်မသုံးရဘူး
- လက်ရှိစာမျက်နှာမှာ မသိမ်းရသေးတဲ့အချက်အလက်ရှိရင် လုပ်ငန်းနယ်ပယ်မပြောင်းခင်
  အသုံးပြုသူကို သတိပေးရမယ်
- အရင်လုပ်ငန်းနယ်ပယ်က အချက်အလက်ကို ဆက်မထားဘဲ အသစ်ရွေးထားတဲ့လုပ်ငန်းနဲ့
  သက်ဆိုင်တဲ့
  အချက်အလက်ကို ပြန်ဖတ်ရမယ်
- လုပ်ငန်းနယ်ပယ်ပြောင်းတဲ့အခါ အသုံးပြုသူ၊ အရင်နယ်ပယ်၊ နယ်ပယ်အသစ်၊ session
  နဲ့ ပြောင်းတဲ့အချိန်ကို စစ်ဆေးမှတ်တမ်းထဲ မှတ်တမ်းတင်ရမယ်

### ၇.၄။ Merchant Applicant နဲ့ Merchant Owner ဝင်ရောက်ခွင့်

ရောင်းချသူလုပ်ငန်း စတင်မယ့် Customer က ပုံမှန် Customer ဝင်ရောက်ခွင့်
မဆုံးရှုံးဘဲ ရောင်းချသူလုပ်ငန်းဖွင့်လှစ်ဖို့ လိုအပ်တဲ့အဆင့်တွေကို
ပြီးဆုံးအောင် လုပ်နိုင်ရပါမယ်။

စနစ်က အောက်ပါအချက်တွေကို လုပ်ပေးရပါမယ် —

- အသက်ဝင်နေတဲ့ အသုံးပြုသူအကောင့်ကို ဖန်တီး သို့မဟုတ် ရှိပြီးသားအကောင့်ကို
  ပြန်သုံးရမယ်။ တူညီတဲ့အကောင့်ကို ထပ်မဖန်တီးရဘူး
- လုပ်ငန်းဖွင့်လှစ်နေစဉ် အသစ်ဖန်တီးထားတဲ့ Merchant Account တစ်ခုတည်းမှာသာ
  အကျိုးသက်ရောက်တဲ့ Merchant Applicant ဝင်ရောက်ခွင့် ပေးရမယ်
- ရောင်းချသူလုပ်ငန်းကို အတည်ပြုပြီးတဲ့အခါ Applicant ဝင်ရောက်ခွင့်ကို
  အဲဒီလုပ်ငန်းအတွက် Merchant Owner ဝင်ရောက်ခွင့်နဲ့ အစားထိုးရမယ်
- ရောင်းချသူလုပ်ငန်းကို ငြင်းပယ်တာ၊ ပြင်ဆင်ချက်တောင်းတာ သို့မဟုတ်
  ယာယီပိတ်တာကြောင့်
  Customer App ဝင်ရောက်ခွင့် မပျက်ရဘူး

### ၇.၅။ နယ်ပယ်ကန့်သတ်ထားတဲ့ ဝန်ထမ်းဖိတ်ခေါ်မှု

Merchant Owner သို့မဟုတ် လုပ်ပိုင်ခွင့်ရှိတဲ့ စီမံခန့်ခွဲသူက ဝန်ထမ်းတစ်ယောက်ကို
သတ်မှတ်ထားတဲ့ ရောင်းချသူလုပ်ငန်း သို့မဟုတ် အွန်လိုင်းဆိုင်တစ်ခုအတွက်
ဖိတ်ခေါ်နိုင်ရပါမယ်။ ဒါမှ ဝန်ထမ်းက သူ့အလုပ်အတွက် လိုအပ်တဲ့ဝင်ရောက်ခွင့်ကိုပဲ
ရမှာပါ။

စနစ်က အောက်ပါအချက်တွေကို လုပ်ပေးရပါမယ် —

- လုပ်ပိုင်ခွင့်ရှိတဲ့ ဖိတ်ခေါ်သူက ပေးမယ့်အခန်းကဏ္ဍနဲ့
  ခွင့်ပြုမယ့်လုပ်ငန်းနယ်ပယ်ကို ရွေးပြီး အီးမေးလ်ဖိတ်ခေါ်မှု ပို့နိုင်ရမယ်
- ဖိတ်ခေါ်သူကို သူ့ကိုယ်ပိုင်လုပ်ပိုင်ခွင့်ထက် ပိုကျယ်တဲ့ အခန်းကဏ္ဍ သို့မဟုတ်
  လုပ်ငန်းနယ်ပယ် ပေးခွင့်မပြုရဘူး
- တစ်ကြိမ်တည်းသုံးလို့ရပြီး သက်တမ်းကုန်ဆုံးချိန်နဲ့ အခြေအနေရှင်းလင်းတဲ့
  လက်ခံရန် link ထုတ်ပေးရမယ်
- ရှိပြီးသားအကောင့်မှာ ဝင်ရောက်ခွင့် ချိတ်ပေးရမယ်။ အကောင့်မရှိသေးရင်
  ဝင်ရောက်ခွင့်မချိတ်ခင် အကောင့်ဖွင့်ခိုင်းရမယ်
- အသုံးပြုပြီးသား၊ သက်တမ်းကုန်ပြီးသား သို့မဟုတ် ဖျက်သိမ်းထားတဲ့
  ဖိတ်ခေါ်မှုကို ငြင်းပယ်ရမယ်

### ၇.၆။ နယ်ပယ်ကန့်သတ်ထားတဲ့ ဝင်ရောက်ခွင့် စီမံခြင်း

လုပ်ပိုင်ခွင့်ရှိတဲ့ Merchant Admin သို့မဟုတ် Platform Admin က
ဝင်ရောက်လုပ်ကိုင်ခွင့်သတ်မှတ်ချက်တွေကို ကြည့်ရှုပြီး ဖယ်ရှားနိုင်ရပါမယ်။
ဒါမှ အလုပ်ထွက်သွားတဲ့ဝန်ထမ်းက လုပ်ငန်းအချက်အလက်တွေကို ဆက်လက်စီမံလို့
မရမှာပါ။

စနစ်က အောက်ပါအချက်တွေကို လုပ်ပေးရပါမယ် —

- လုပ်ပိုင်ခွင့်ရှိသူက အသက်ဝင်၊ ယာယီပိတ်၊ သက်တမ်းကုန်နဲ့ ရုပ်သိမ်းပြီးသား
  ဝင်ရောက်လုပ်ကိုင်ခွင့်သတ်မှတ်ချက်တွေကို ကြည့်နိုင်ရမယ်
- စည်းမျဉ်းအရ ခွင့်ပြုထားတဲ့ဝင်ရောက်ခွင့်ကို ပေးခြင်း၊ ယာယီပိတ်ခြင်း၊
  ပြန်ဖွင့်ခြင်း၊ ရုပ်သိမ်းခြင်းနဲ့ သက်တမ်းကုန်ဆုံးချိန် သတ်မှတ်ခြင်းတို့ကို
  လုပ်နိုင်ရမယ်
- ရုပ်သိမ်း သို့မဟုတ် ယာယီပိတ်ထားတဲ့ဝင်ရောက်ခွင့်က နောက်ထပ်ကာကွယ်ထားတဲ့
  တောင်းဆိုမှုကို စစ်တဲ့အချိန်ကစပြီး လုပ်ပိုင်ခွင့် မပေးရတော့ဘူး
- အသုံးပြုသူက ကိုယ့်ဝင်ရောက်ခွင့်ကို ကိုယ်တိုင်အတည်ပြုတာ သို့မဟုတ်
  လုပ်ပိုင်ခွင့်ပိုကျယ်အောင် ချဲ့တာ မလုပ်နိုင်ရဘူး

### ၇.၇။ လုပ်ငန်းအချက်အလက် နယ်ပယ်ခွဲခြားကာကွယ်ခြင်း

စနစ်က ရောင်းချသူလုပ်ငန်းတစ်ခုရဲ့ ကိုယ်ပိုင်လုပ်ငန်းအချက်အလက်ကို
တခြားရောင်းချသူလုပ်ငန်းတွေ ဝင်ရောက်မကြည့်နိုင်အောင် ကာကွယ်ရပါမယ်။

စနစ်က အောက်ပါအချက်တွေကို လုပ်ပေးရပါမယ် —

- Merchant-level ဝင်ရောက်ခွင့်ကို အဲဒီရောင်းချသူလုပ်ငန်း ပိုင်ဆိုင်ကြောင်း
  အတည်ပြုထားတဲ့ အချက်အလက်နဲ့ လုပ်ငန်းပိုင်ပစ္စည်းတွေအတွက်ပဲ အသုံးပြုရမယ်
- Storefront-level ဝင်ရောက်ခွင့်က တူညီတဲ့ Merchant အောက်မှာရှိတဲ့
  တခြားအွန်လိုင်းဆိုင်တွေကို ဝင်ရောက်ခွင့်မပေးရဘူး
- Catalog၊ Inventory၊ Merchant နဲ့ Order လုပ်ဆောင်ချက်တိုင်းမှာ အသုံးပြုသူရဲ့
  လုပ်ပိုင်ခွင့်နဲ့ တောင်းဆိုထားတဲ့အရာရဲ့ ပိုင်ဆိုင်မှု နှစ်ခုလုံးကို
  စစ်ဆေးရမယ်
- လုပ်ပိုင်ခွင့်နယ်ပယ် (`scope`) မကိုက်ညီရင် ကာကွယ်ထားတဲ့အချက်အလက်ကို
  မဖော်ပြဘဲ ဝင်ရောက်ခွင့်မရှိကြောင်း ပြန်ပေးရမယ်

### ၇.၈။ Context နဲ့ ချိတ်ထားတဲ့ Session

စနစ်ဝင်အသုံးပြုနေချိန် (`session`) က ရွေးထားတဲ့လုပ်ငန်းနဲ့
ဆက်ချိတ်ထားရပါမယ်။ Session သက်တမ်းတိုးတာကြောင့် အသုံးပြုသူမသိဘဲ
တခြားလုပ်ငန်းတစ်ခုကို ပြောင်းမသွားရပါဘူး။

စနစ်က အောက်ပါအချက်တွေကို လုပ်ပေးရပါမယ် —

- ကာကွယ်ထားတဲ့ session တစ်ခုမှာ လက်ရှိသုံးနေတဲ့ App နဲ့
  အသက်ဝင်နေတဲ့လုပ်ငန်းနယ်ပယ်ကို ခွဲခြားသိနိုင်ရမယ်
- Session သက်တမ်းတိုးတဲ့အခါ အရင် App၊ ဝင်ရောက်ခွင့်သတ်မှတ်ချက်နဲ့
  လုပ်ပိုင်ခွင့်နယ်ပယ်ကိုပဲ
  ဆက်ထိန်းထားရမယ်
- စနစ်ထွက်တဲ့အခါ လက်ရှိ refresh session ကို ပြန်သုံးလို့မရအောင်
  ရုပ်သိမ်းရမယ်
- ဝင်ရောက်ခွင့်သတ်မှတ်ချက်တစ်ခုကို ဖယ်ရှားတဲ့အခါ အဲဒီသတ်မှတ်ချက်နဲ့
  ချိတ်ထားတဲ့ session တွေကို ရုပ်သိမ်းရမယ်။ မသက်ဆိုင်တဲ့ တခြား session
  တွေကို မထိခိုက်ရဘူး

## ၈။ လုပ်ငန်းစည်းမျဉ်းများ

- Identity assignment မှန်ကန်နေရုံနဲ့ အသက်မဝင်တဲ့ Merchant၊ Storefront
  သို့မဟုတ် Location ကို အသုံးပြုခွင့်မရဘူး။ Resource ကို ပိုင်ဆိုင်တဲ့ module
  က လုပ်ငန်းအခြေအနေကို ဆက်စစ်ရမယ်
- Platform နဲ့ scope တန်ဖိုးတွေကို server က စစ်ဆေးရမယ်။ Client ကပေးတဲ့
  တန်ဖိုးတွေက `context` ရွေးဖို့ တောင်းဆိုချက်သာဖြစ်ပြီး ယုံကြည်ရတဲ့
  authorization အချက်အလက် မဟုတ်ဘူး
- Provider role သို့မဟုတ် token claim က မစစ်ဆေးရသေးတဲ့ Merchant၊ Storefront
  သို့မဟုတ် Fulfillment Location scope ကို တိုက်ရိုက်ပေးလို့ မရဘူး
- Unauthorized နဲ့ Forbidden request တွေအတွက် လက်ရှိသုံးနေတဲ့
  `RFC 7807` error response ပုံစံကိုပဲ ဆက်သုံးရမယ်
- ဝင်ရောက်ခွင့်စစ်ဆေးမှုကြောင့် platform ရဲ့ authentication response time
  ရည်မှန်းချက်ကို သိသိသာသာ မနှေးစေရဘူး
- Client ပေးတဲ့ actor သို့မဟုတ် ပိုင်ဆိုင်မှု ID ကို resource input အဖြစ်သာ
  သတ်မှတ်ရမယ်။ Identity သို့မဟုတ် authorization အထောက်အထားအဖြစ် မယူရဘူး
- ရွေးထားတဲ့ `context` ကို အသုံးမပြုနိုင်တော့ရင် စနစ်က အသုံးပြုသူမသိဘဲ
  တခြား Merchant တစ်ခုကို အလိုအလျောက် မပြောင်းရဘူး

## ၉။ အောင်မြင်တယ်လို့ သတ်မှတ်မယ့်အချက်များ

အောက်ပါအချက်တွေအားလုံး ပြည့်မီရင် ဒီ module အောင်မြင်တယ်လို့ သတ်မှတ်ပါမယ် —

- Customer၊ Seller Portal နဲ့ Admin Console role တွေက သတ်မှတ်ထားတဲ့
  platform မှာပဲ အကျိုးသက်ရောက်ရမယ်
- Merchant A ရဲ့ အသုံးပြုသူက Merchant B ရဲ့ resource တွေကို ဖတ်ခြင်း
  သို့မဟုတ် ပြင်ဆင်ခြင်း မလုပ်နိုင်ကြောင်း automated test နဲ့ သက်သေပြရမယ်
- Merchant၊ Storefront နဲ့ Fulfillment Location scope အလိုက် ငြင်းပယ်မှု
  test တွေက Catalog၊ Inventory၊ Merchant နဲ့ လက်ရှိရရှိနိုင်တဲ့ Order
  လုပ်ဆောင်ချက်တွေမှာ အောင်မြင်ရမယ်
- Login၊ refresh၊ `context` ပြောင်းခြင်း၊ logout၊ assignment ရုပ်သိမ်းခြင်းနဲ့
  session သက်တမ်းကုန်ခြင်းတို့မှာ `context` အပြုအမူ မှန်ကန်ရမယ်
- ရှိပြီးသား Customer နဲ့ Admin assignment တွေကို မှန်ကန်စွာ
  ပြန်လည်ကိုက်ညီအောင် ပြောင်းရွှေ့ပြီးဖြစ်ရမယ်
- ကာကွယ်ထားတဲ့ API တွေက authorization အတွက် `X-Actor-Id`၊ Client
  ရွေးပေးတဲ့ `sellerId` သို့မဟုတ် အလားတူတန်ဖိုးတွေကို မမှီခိုရတော့ဘူး
- Merchant တစ်ခုကနေ တခြား Merchant တစ်ခုရဲ့အချက်အလက် ပေါက်ကြားမှု
  အတည်ပြုဖြစ်စဉ်အရေအတွက် `0` ဖြစ်ရမယ်
- အတည်ပြုထားတဲ့ `context` ပါတဲ့ Seller Portal protected request
  အချိုး `100%` ဖြစ်ရမယ်
- လက်ခံပြီးတဲ့ ဝန်ထမ်းဖိတ်ခေါ်မှုကြောင့် Merchant သို့မဟုတ် Storefront
  ထပ်ဖန်တီးမိတဲ့အရေအတွက် `0` ဖြစ်ရမယ်
- Merchant ကို ယာယီပိတ်ခြင်းကြောင့် မသက်ဆိုင်တဲ့ Customer App ဝင်ရောက်ခွင့်
  ပိတ်သွားတဲ့အရေအတွက် `0` ဖြစ်ရမယ်

## ၁၀။ နည်းပညာဆိုင်ရာ ထည့်သွင်းစဉ်းစားချက်နဲ့ ကန့်သတ်ချက်များ

- **အဓိကအချက်အလက်ပိုင်ရှင်:** Identity က User၊ Platform၊ Role၊
  Access Assignment၊ Invitation နဲ့ Session Context တို့အတွက် အဓိက
  အချက်အလက်ပိုင်ရှင် ဖြစ်ပါတယ်။ Merchant Account နဲ့ Storefront အတွက်
  Merchant က ပိုင်ရှင်ဖြစ်ပြီး Fulfillment Location အတွက် Inventory က
  ပိုင်ရှင်ဖြစ်ပါတယ်
- **Provider နဲ့ ကိုက်ညီမှု:** Access resolution က လက်ရှိ local
  authentication နဲ့ နောင်သုံးမယ့် OAuth2/OIDC provider နှစ်မျိုးလုံးမှာ
  ဆက်လက်အလုပ်လုပ်ရမယ်
- **Tracking Event များ:** အဓိကလုပ်ဆောင်ချက်တွေအတွက်
  `platform_access_resolved`၊ `platform_access_denied`၊ `context_selected`၊
  `context_switch_succeeded`၊ `scope_access_denied`၊
  `access_assignment_granted`၊ `access_invitation_sent` နဲ့
  `access_invitation_accepted` event တွေ ထုတ်ရမယ်
- **ပြောင်းရွှေ့မှုကန့်သတ်ချက်:** Legacy assignment နဲ့ assignment အသစ်ကို
  ပြောင်းရွှေ့နေချိန်မှာ တပြိုင်နက် ဖတ်နိုင်ပေမယ့် ဝင်ရောက်ခွင့်ပိုကျယ်သွားအောင်
  နှစ်ခုကို ပေါင်းမသုံးရဘူး။ Assignment အရေအတွက်နဲ့ resource ပိုင်ဆိုင်မှု
  မှန်ကန်ကြောင်း စစ်ဆေးပြီးမှ role အဟောင်းတွေကို ဖယ်ရှားရမယ်
- **Platform ပံ့ပိုးမှု:** Version 1 မှာ shared Identity API တွေကနေ
  Customer App၊ Seller Portal နဲ့ Admin Console ရဲ့ web/mobile client တွေကို
  ပံ့ပိုးရမယ်

## ၁၁။ မှီခိုနေတဲ့ Module နဲ့ အစိတ်အပိုင်းများ

- Merchant နဲ့ Storefront ရှိ၊ မရှိ၊ ပိုင်ဆိုင်မှုနဲ့ lifecycle အတွက်
  Merchant module ကို မှီခိုပါတယ်
- Fulfillment Location ပိုင်ဆိုင်မှုနဲ့ lifecycle အတွက် Inventory module ကို
  မှီခိုပါတယ်
- Platform အများအပြားကို ပံ့ပိုးဖို့ Framework အခြေခံအစိတ်အပိုင်းတွေနဲ့
  shared Identity API တွေကို မှီခိုပါတယ်
