# ထုတ်ကုန်လိုအပ်ချက် သတ်မှတ်ချက်စာတမ်း — အသုံးပြုသူစိစစ်ရေး ကဏ္ဍ

## ၁။ အကျဉ်းချုပ်

ဒီစာတမ်းက အွန်လိုင်းဈေးရောင်းဈေးဝယ်စနစ်မှာ အသုံးပြုသူစိစစ်ရေး ကဏ္ဍက
ဘာတွေလုပ်ပေးရမလဲဆိုတာ သတ်မှတ်ထားတာပါ။

ဒီကဏ္ဍရဲ့ အဓိကတာဝန်က အသုံးပြုသူတစ်ယောက်ချင်းစီရဲ့ အချက်အလက်၊
စနစ်ဝင်ရောက်ခွင့်နဲ့ လုပ်ပိုင်ခွင့်တွေကို မှန်မှန်ကန်ကန် ထိန်းထားပေးဖို့ ဖြစ်ပါတယ်။
တောင်းဆိုမှုတစ်ခု ဝင်လာတိုင်း —

- တောင်းဆိုတဲ့သူက ဘယ်သူလဲ
- သူ့မှာ ဘာအခန်းကဏ္ဍရှိလဲ
- သူတောင်းဆိုတဲ့အလုပ်ကို လုပ်ခွင့်ရှိလား

ဆိုတာတွေကို စနစ်က ယုံယုံကြည်ကြည် စစ်ဆေးနိုင်ရပါမယ်။

## ၂။ ဘာပြဿနာကို ဖြေရှင်းမှာလဲ

အွန်လိုင်းဈေးရောင်းဈေးဝယ်စနစ်တစ်ခုမှာ `ရောင်းချသူ`က ကိုယ်ပိုင်ကုန်ပစ္စည်းနဲ့
ကုန်လက်ကျန်ကိုပဲ ပြင်ဆင်နိုင်ရပါမယ်။ `စနစ်အုပ်ချုပ်သူ`ကလည်း စနစ်တစ်ခုလုံးကို
စီမံနိုင်ရပါမယ်။ `ဖောက်သည်`တွေကလည်း စိတ်ချလက်ချ ကြည့်ရှုဝယ်ယူနိုင်ရပါမယ်။
ဒါတွေအတွက် ဘယ်သူက ဘာလုပ်ခွင့်ရှိတယ်ဆိုတာ တိတိကျကျ သိဖို့လိုပါတယ်။

ဒီကဏ္ဍမရှိရင် —

- မည်သူမဆို `X-Actor-Id` header ကို စိတ်ကြိုက်ထည့်ပြီး တခြားအသုံးပြုသူအဖြစ်
  ဟန်ဆောင်နိုင်တယ်
- `ရောင်းချသူ`တစ်ယောက်က တခြား`ရောင်းချသူ`ရဲ့ ကုန်ပစ္စည်းနဲ့ ကုန်လက်ကျန်ကို
  ဝင်ပြင်နိုင်တယ်
- ကုန်ပစ္စည်းအတည်ပြုတာလို `စနစ်အုပ်ချုပ်သူ`ပဲ လုပ်သင့်တဲ့အလုပ်တွေကို
  မည်သူမဆို လုပ်နိုင်တယ်
- အကောင့်ဖွင့်တာ၊ စနစ်ဝင်တာမျိုး မလုပ်နိုင်ဘူး
- `စနစ်အုပ်ချုပ်သူ`၊ `ရောင်းချသူ`နဲ့ `ဖောက်သည်`တို့ရဲ့ လုပ်ဆောင်ချက်တွေကို
  ခွဲခြားလို့မရဘူး
- စနစ်မဝင်ထားသူတွေကို ဖွင့်ပေးချင်တဲ့ ဆိုင်မျက်နှာစာလမ်းကြောင်းတွေကို
  သီးသန့်ရွေးပြီး ဖွင့်ပေးလို့မရဘူး

## ၃။ ဘယ်သူတွေ အသုံးပြုမှာလဲ

- ပလက်ဖောင်းကို စီမံခန့်ခွဲမယ့် `စနစ်အုပ်ချုပ်သူ`
- လက်လီ၊ ပြင်ပလုပ်ငန်း သို့မဟုတ် လူတစ်ဦးချင်းအနေနဲ့ ရောင်းချမယ့် `ရောင်းချသူ`
- ပစ္စည်းဝယ်ယူမယ့် `ဖောက်သည်`
- စနစ်မဝင်ဘဲ ဆိုင်မျက်နှာစာကို လာကြည့်မယ့်သူ

## ၄။ ရည်ရွယ်ချက်

- အသုံးပြုသူတွေ လုံလုံခြုံခြုံ အကောင့်ဖွင့်ပြီး စနစ်ဝင်နိုင်ဖို့
- အပလီကေးရှင်းလမ်းကြောင်းအားလုံးမှာ အခန်းကဏ္ဍအလိုက် လုပ်ပိုင်ခွင့်စစ်ဖို့
- `ရောင်းချသူ`အဖြစ် အကောင့်ဖွင့်ပြီးရင် `စနစ်အုပ်ချုပ်သူ`က အတည်ပြုပေးတဲ့
  လုပ်ငန်းစဉ် ရှိဖို့
- ဆိုင်မျက်နှာစာက ကုန်ပစ္စည်းကြည့်တဲ့ လမ်းကြောင်းတွေကို အများသုံးအဖြစ်
  ဆက်ဖွင့်ထားဖို့
- နောင်မှာ Keycloak၊ Auth0၊ Cognito လို ပြင်ပ `OAuth2/OIDC` ဝန်ဆောင်မှုကို
  ပြောင်းသုံးချင်ရင် လုပ်ငန်းကုဒ်တွေ အများကြီးပြန်ပြင်စရာမလိုဖို့

## ၅။ ဒီကဏ္ဍထဲမှာ ပါရမယ့်အရာတွေ

- အီးမေးလ်နဲ့ စကားဝှက်သုံးပြီး အကောင့်ဖွင့်ခြင်း
- အသုံးပြုသူမှန်ကန်ကြောင်း စစ်ဆေးပြီး `JWT` တိုကင် ထုတ်ပေးခြင်း
- စနစ်ဝင်ထားတဲ့အချိန်ကို သက်တမ်းတိုးနိုင်ဖို့ refresh token ထုတ်ပေးပြီး
  အသစ်နဲ့ လဲပေးခြင်း
- အစကတည်းက ထည့်ထားမယ့် `စနစ်အုပ်ချုပ်သူ`၊ `ရောင်းချသူ`နဲ့ `ဖောက်သည်`
  အခန်းကဏ္ဍတွေ
- `စနစ်အုပ်ချုပ်သူ`က အခန်းကဏ္ဍအသစ် ဖန်တီးတာ၊ ဖွင့်တာ၊ ပိတ်တာနဲ့
  အသုံးပြုသူကို သတ်မှတ်ပေးတာ
- အခန်းကဏ္ဍတစ်ခုချင်းစီကို စနစ်ထဲက လုပ်ပိုင်ခွင့်တွေနဲ့ ချိတ်ပေးတာ
- `ရောင်းချသူ`အကောင့်ကို အတည်ပြုချက်စောင့်နေတဲ့အခြေအနေနဲ့ စဖွင့်ပေးတာ
- `ရောင်းချသူ`အကောင့်ကို `စနစ်အုပ်ချုပ်သူ`က အတည်ပြုတာ သို့မဟုတ် ငြင်းပယ်တာ
- အသုံးပြုသူအကောင့်ကို အသက်ဝင်၊ အတည်ပြုချက်စောင့်၊ ယာယီပိတ် စတဲ့
  အခြေအနေတွေနဲ့ ထိန်းတာ
- စကားဝှက်ကို `BCrypt` နဲ့ ဖတ်မရအောင် ပြောင်းပြီးမှ သိမ်းတာ
- စနစ်ဝင်ရောက်ခွင့်လိုတဲ့ တောင်းဆိုမှုတိုင်းမှာ `JWT` တိုကင်ကို စစ်တာ
- ဘယ်တိုကင်ဝန်ဆောင်မှုကို သုံးထားတယ်ဆိုတာနဲ့ မသက်ဆိုင်တဲ့ Bearer တိုကင်
  စစ်ဆေးရေးပုံစံတစ်ခု ထားတာ
- လမ်းကြောင်းတစ်ခုချင်းစီကို အခန်းကဏ္ဍနဲ့ လုပ်ပိုင်ခွင့်အလိုက် ကာကွယ်တာ
- ဆိုင်မျက်နှာစာကြည့်ဖို့ အများသုံးလမ်းကြောင်းတွေကို သီးသန့်သတ်မှတ်တာ
- အသုံးပြုသူက ကိုယ့်အကောင့်အချက်အလက်ကို ပြန်ကြည့်နိုင်တာ
- စနစ်ထွက်တဲ့အခါ refresh token ကို ပြန်သုံးလို့မရအောင် ပိတ်တာ
- 401 နဲ့ 403 အမှားတွေကို `RFC 7807 ProblemDetail` ပုံစံနဲ့ ပြန်ပေးတာ

## ၆။ ဒီကဏ္ဍထဲမှာ မပါသေးတဲ့အရာတွေ

- Google၊ Facebook၊ Apple အကောင့်နဲ့ တိုက်ရိုက်စနစ်ဝင်ခြင်း
- အဆင့်နှစ်ဆင့် သို့မဟုတ် အဆင့်များစွာနဲ့ အသုံးပြုသူစစ်ဆေးခြင်း
- အီးမေးလ်အတည်ပြုခြင်းနဲ့ စကားဝှက်မေ့ရင် ပြန်သတ်မှတ်ပေးခြင်း
- ဒီဈေးရောင်းဈေးဝယ်စနစ်ကိုယ်တိုင် `OAuth2 authorization server` သို့မဟုတ်
  `OpenID Connect provider` အဖြစ် လုပ်ဆောင်ခြင်း။ ဒီတာဝန်တွေကို နောင်မှာ
  ပြင်ပဝန်ဆောင်မှုတစ်ခုက ယူနိုင်ပါတယ်
- အသုံးပြုသူဓာတ်ပုံနဲ့ တခြားကိုယ်ရေးအချက်အလက် အသေးစိတ်တွေ
- အသုံးပြုသူစိတ်ကြိုက် လုပ်ပိုင်ခွင့်ဖန်တီးတာ သို့မဟုတ် အရင်းအမြစ်တစ်ခုချင်းစီကို
  စိတ်ကြိုက်ဝင်ခွင့်ပေးတာ။ စနစ်က သတ်မှတ်ထားတဲ့ လုပ်ပိုင်ခွင့်စာရင်းကိုပဲ
  အခန်းကဏ္ဍတွေနဲ့ ချိတ်သုံးရပါမယ်
- အပလီကေးရှင်းသုံး သော့ချက်တွေကို စီမံတာ
- တောင်းဆိုမှုအကြိမ်ရေ ကန့်သတ်တာနဲ့ စကားဝှက်ကို အကြိမ်ကြိမ်စမ်းတဲ့
  တိုက်ခိုက်မှုတွေ ကာကွယ်တာ
- စနစ်ဝင်ဖို့ ကြိုးစားမှုတိုင်းကို စစ်ဆေးမှတ်တမ်းတင်တာ

## ၇။ အဓိကလုပ်ဆောင်ချက်တွေ

### ၇.၁။ အကောင့်ဖွင့်ခြင်း

အသုံးပြုသူက အီးမေးလ်နဲ့ စကားဝှက်သုံးပြီး အကောင့်ဖွင့်နိုင်ရပါမယ်။

အကောင့်ဖွင့်တဲ့အခါ —

- အီးမေးလ်နဲ့ စကားဝှက် မဖြစ်မနေ ထည့်ရမယ်
- `ရောင်းချသူ` သို့မဟုတ် `ဖောက်သည်`အဖြစ် ရွေးနိုင်ရမယ်
- အီးမေးလ်ပုံစံ မှန်၊ မမှန်နဲ့ တခြားအကောင့်မှာ သုံးထားပြီးသားလားဆိုတာ
  စစ်ရမယ်
- စကားဝှက်ကို `BCrypt` နဲ့ ပြောင်းပြီးမှ သိမ်းရမယ်
- `ဖောက်သည်`အကောင့်ကို `ACTIVE` အနေနဲ့ ချက်ချင်းဖွင့်ပေးရမယ်
- `ရောင်းချသူ`အကောင့်ကို `PENDING_APPROVAL` အနေနဲ့ ဖွင့်ပေးရမယ်
- `ဖောက်သည်`အကောင့်ဖွင့်ပြီးရင် access token နဲ့ refresh token ပါတဲ့
  `JWT` တိုကင်အတွဲကို ပြန်ပေးရမယ်
- `ရောင်းချသူ`အကောင့်ဖွင့်ပြီးရင် အတည်ပြုချက်စောင့်နေကြောင်းပဲ ပြောရမယ်။
  အသုံးပြုလို့ရတဲ့ တိုကင် မပေးရဘူး

### ၇.၂။ စနစ်ဝင်ခြင်း

အသုံးပြုသူက အီးမေးလ်နဲ့ စကားဝှက်သုံးပြီး စနစ်ဝင်နိုင်ရပါမယ်။

စနစ်ဝင်တဲ့အခါ —

- အီးမေးလ်နဲ့ စကားဝှက်ကို လက်ခံရမယ်
- ထည့်လိုက်တဲ့ စကားဝှက်နဲ့ သိမ်းထားတဲ့ `BCrypt` တန်ဖိုး ကိုက်ညီလား
  စစ်ရမယ်
- အကောင့်အခြေအနေက `ACTIVE` မဟုတ်ရင် စနစ်ဝင်ခွင့် မပေးရဘူး
- issuer၊ subject၊ platform user ID၊ အီးမေးလ်နဲ့ အခန်းကဏ္ဍတွေပါတဲ့
  `JWT` access token ထုတ်ပေးရမယ်
- စနစ်ဝင်ထားတဲ့အချိန်ကို သက်တမ်းတိုးနိုင်ဖို့ refresh token ပေးရမယ်
- တိုကင်ဘယ်အချိန် သက်တမ်းကုန်မယ်ဆိုတာ ပြန်ပြောရမယ်

### ၇.၃။ တိုကင်စီမံခြင်း

ဆာဗာဘက်မှာ စနစ်ဝင်အခြေအနေကို အမြဲသိမ်းမထားရတဲ့ `JWT` အခြေပြု
စစ်ဆေးမှုကို သုံးရပါမယ်။

- လက်မှတ်ထိုးထားပြီး သက်တမ်းကို ချိန်ညှိလို့ရတဲ့ `JWT` access token
  ထုတ်ပေးရမယ်
- `iss`၊ `sub`၊ `aud`၊ `iat`၊ `exp` ဆိုတဲ့ စံ claim တွေ ပါရမယ်
- `platform_user_id` နဲ့ အခန်းကဏ္ဍကုဒ်စာရင်းဖြစ်တဲ့ `roles` claim ပါရမယ်
- စနစ်ဝင်ရောက်ခွင့်လိုတဲ့ တောင်းဆိုမှုတိုင်းမှာ တိုကင်ကို စစ်ရမယ်
- refresh token သုံးလိုက်တိုင်း access token နဲ့ refresh token အသစ်
  ထုတ်ပေးပြီး refresh token အဟောင်းကို ပိတ်ရမယ်
- refresh token အစစ်ကို ဒေတာဘေ့စ်ထဲ မသိမ်းရဘူး။ ပြန်ဖတ်လို့မရတဲ့
  cryptographic hash ကိုပဲ သိမ်းရမယ်
- စနစ်ထွက်လိုက်ရင် refresh token ကို ပြန်သုံးလို့မရအောင် လုပ်ရမယ်

### ၇.၄။ အခန်းကဏ္ဍအလိုက် လုပ်ပိုင်ခွင့်ထိန်းချုပ်ခြင်း

စနစ်ထဲမှာ လုပ်ပိုင်ခွင့်တွေကို တည်ငြိမ်အောင် သတ်မှတ်ထားပြီး အခန်းကဏ္ဍတွေကို
အဲဒီလုပ်ပိုင်ခွင့်တွေနဲ့ ချိတ်သုံးရပါမယ်။ ဒီလိုလုပ်ထားရင် `စနစ်အုပ်ချုပ်သူ`က
အခန်းကဏ္ဍအသစ် ထပ်ဖန်တီးတဲ့အခါ လမ်းကြောင်းကာကွယ်ထားတဲ့ကုဒ်တွေကို
ပြန်ပြင်စရာ မလိုတော့ပါဘူး။

အစကတည်းက အောက်ပါအခန်းကဏ္ဍသုံးခု ထည့်ထားရပါမယ် —

- **ADMIN** — ကုန်ပစ္စည်းအတည်ပြုတာ၊ အသုံးပြုသူစီမံတာ၊ အစုလိုက်လုပ်ဆောင်တာ
  အပါအဝင် အားလုံးကို လုပ်ခွင့်ရှိတယ်
- **SELLER** — ကုန်ပစ္စည်းနဲ့ ကုန်လက်ကျန်ကို ဖန်တီး၊ ကြည့်၊ ပြင်၊ ဖျက်နိုင်ပြီး
  ကိုယ့်အကောင့်အချက်အလက်ကို စီမံနိုင်တယ်
- **CUSTOMER** — ဆိုင်မျက်နှာစာကြည့်တာ၊ ပစ္စည်းဝယ်တာနဲ့
  ကိုယ့်အကောင့်အချက်အလက်ကို စီမံတာ လုပ်နိုင်တယ်

အခန်းကဏ္ဍတွေအတွက် စည်းမျဉ်းတွေက —

- အခန်းကဏ္ဍကုဒ်က မတူရဘူး၊ ဖန်တီးပြီးရင်လည်း အမည်ပြောင်းလို့မရဘူး
- လူဖတ်ဖို့သုံးတဲ့ အခန်းကဏ္ဍအမည်နဲ့ ရှင်းလင်းချက်ကိုတော့ ပြင်လို့ရမယ်
- `စနစ်အုပ်ချုပ်သူ`က အခန်းကဏ္ဍဖန်တီး၊ ဖွင့်၊ ပိတ်၊ အသုံးပြုသူကို သတ်မှတ်
  ပေးနိုင်ရမယ်
- `စနစ်အုပ်ချုပ်သူ`က အခန်းကဏ္ဍကို စနစ်ထဲမှာ သတ်မှတ်ထားတဲ့
  လုပ်ပိုင်ခွင့်တွေနဲ့ ချိတ်နိုင်ရမယ်
- ပိတ်ထားတဲ့ အခန်းကဏ္ဍက ဘာလုပ်ပိုင်ခွင့်မှ မပေးရဘူး
- လမ်းကြောင်းကာကွယ်တဲ့ကုဒ်က `PRODUCT_WRITE_OWN`၊ `PRODUCT_WRITE_ANY`၊
  `PRODUCT_MODERATE`၊ `INVENTORY_MANAGE_OWN`၊ `INVENTORY_MANAGE_ANY`၊
  `SELLER_APPROVE`၊ `ROLE_MANAGE` လို လုပ်ပိုင်ခွင့်ကုဒ်တွေကို စစ်ရမယ်
- လုပ်ပိုင်ခွင့်စစ်ပြီးရင်တောင် `ရောင်းချသူ`က ကိုယ်ပိုင်အရင်းအမြစ်ကိုပဲ
  ကိုင်တွယ်နေတာ ဟုတ်၊ မဟုတ်ကို platform user ID သုံးပြီး ထပ်စစ်ရမယ်

### ၇.၅။ စနစ်မဝင်ဘဲ အသုံးပြုလို့ရမယ့် လမ်းကြောင်းတွေ

အောက်ပါလုပ်ဆောင်ချက်တွေကို စနစ်မဝင်ထားသူကလည်း အသုံးပြုနိုင်ရပါမယ် —

- အကောင့်ဖွင့်ခြင်း
- စနစ်ဝင်ခြင်း
- တိုကင်သက်တမ်းတိုးခြင်း
- အဓိက အပလီကေးရှင်းလမ်းကြောင်းကို ကြည့်ခြင်း
- ကုန်ပစ္စည်းကို ID နဲ့ အသေးစိတ်ကြည့်ခြင်း
- ကုန်ပစ္စည်းကို slug နဲ့ အသေးစိတ်ကြည့်ခြင်း
- ကုန်ပစ္စည်းရှာခြင်း
- ကုန်ပစ္စည်းအမျိုးအစားတွေ ကြည့်ခြင်း
- `OpenAPI` စာတမ်းနဲ့ `Swagger UI` ကြည့်ခြင်း

### ၇.၆။ `ရောင်းချသူ`အကောင့် အတည်ပြုခြင်း

`ရောင်းချသူ`အကောင့်ကို `စနစ်အုပ်ချုပ်သူ`က စစ်ပြီးမှ အသက်သွင်းပေးရပါမယ်။

- စဖွင့်တဲ့ `ရောင်းချသူ`အကောင့်ကို `PENDING_APPROVAL` အဖြစ်ထားရမယ်
- စောင့်ဆိုင်းနေချိန်မှာ စနစ်ဝင်ခွင့် မပေးရဘူး
- `စနစ်အုပ်ချုပ်သူ`က အတည်ပြုလိုက်ရင် `ACTIVE` အဖြစ် ပြောင်းရမယ်
- `စနစ်အုပ်ချုပ်သူ`က `ရောင်းချသူ`ကို ငြင်းပယ်တာ သို့မဟုတ် ယာယီပိတ်တာ
  လုပ်နိုင်ရမယ်
- `ရောင်းချသူ`အခြေအနေပြောင်းတိုင်း သက်ဆိုင်ရာ domain event ထုတ်ရမယ်

### ၇.၇။ အသုံးပြုသူအကောင့်ရဲ့ အခြေအနေတွေ

အသုံးပြုသူအကောင့်မှာ အောက်ပါအခြေအနေတွေ ရှိပါမယ် —

- **ACTIVE** — စနစ်ဝင်လို့ရပြီး ကိုယ့်အခန်းကဏ္ဍနဲ့ ကိုက်ညီတဲ့အလုပ်တွေ
  လုပ်လို့ရတယ်
- **PENDING_APPROVAL** — `စနစ်အုပ်ချုပ်သူ` အတည်ပြုတာကို စောင့်နေတဲ့
  `ရောင်းချသူ`အကောင့်ဖြစ်လို့ စနစ်ဝင်လို့မရသေးဘူး
- **SUSPENDED** — ယာယီပိတ်ထားတဲ့အကောင့်ဖြစ်လို့ စနစ်ဝင်လို့မရဘူး

အခြေအနေပြောင်းပုံက —

- `ဖောက်သည်`အကောင့်ဖွင့်ခြင်း → `ACTIVE`
- `ရောင်းချသူ`အကောင့်ဖွင့်ခြင်း → `PENDING_APPROVAL`
- `စနစ်အုပ်ချုပ်သူ` အတည်ပြုခြင်း → `ACTIVE`
- `စနစ်အုပ်ချုပ်သူ` ယာယီပိတ်ခြင်း → `SUSPENDED`
- `စနစ်အုပ်ချုပ်သူ` ပြန်ဖွင့်ပေးခြင်း → `ACTIVE`

### ၇.၈။ အမှားဖြစ်ရင် ဘယ်လိုပြန်မလဲ

လုံခြုံရေးနဲ့ဆိုင်တဲ့ အမှားတွေကို လက်ရှိသုံးနေတဲ့ `RFC 7807 ProblemDetail`
ပုံစံအတိုင်း ပြန်ပေးရပါမယ်။

- **401 Unauthorized** — တိုကင်မပါဘူး၊ တိုကင်သက်တမ်းကုန်နေတယ်၊
  တိုကင်မမှန်ဘူး သို့မဟုတ် အကောင့်အသက်မဝင်ဘူး
- **403 Forbidden** — အသုံးပြုသူက စနစ်ဝင်ထားပေမယ့် တောင်းဆိုတဲ့အလုပ်ကို
  လုပ်ဖို့ လုပ်ပိုင်ခွင့်မရှိဘူး

အမှားအဖြေထဲမှာ `status`၊ `title`၊ `detail`၊ `code`၊ `traceId`၊ `path`၊
`timestamp` နဲ့ `module` ပါရပါမယ်။ လက်ရှိ `GlobalApiExceptionHandler`
ပြန်ပေးနေတဲ့ ပုံစံနဲ့လည်း တူရပါမယ်။

## ၈။ မဖြစ်မနေ လိုက်နာရမယ့် စည်းမျဉ်းတွေ

- အီးမေးလ်တစ်ခုကို အကောင့်တစ်ခုမှာပဲ သုံးလို့ရမယ်
- စကားဝှက်အစစ်ကို ဘယ်တော့မှ မသိမ်းရဘူး။ `BCrypt` နဲ့ ပြောင်းပြီးသား
  တန်ဖိုးကိုပဲ သိမ်းရမယ်
- `ACTIVE` အကောင့်ပဲ စနစ်ဝင်လို့ရမယ်
- `ရောင်းချသူ`က ပထမဆုံးစနစ်မဝင်ခင် `စနစ်အုပ်ချုပ်သူ`ရဲ့ အတည်ပြုချက်
  ရထားရမယ်
- `JWT` access token သက်တမ်းကို ပြင်ဆင်သတ်မှတ်လို့ရမယ်
  (မူလသတ်မှတ်ချက် — ၁ နာရီ)
- refresh token သက်တမ်းကို ပြင်ဆင်သတ်မှတ်လို့ရမယ်
  (မူလသတ်မှတ်ချက် — ၇ ရက်)
- refresh token အသစ်ထုတ်လိုက်တိုင်း အဟောင်းကို ပြန်သုံးလို့မရအောင် ပိတ်ရမယ်
- **ADMIN** အဖြစ် ကိုယ့်ဘာသာ အကောင့်ဖွင့်လို့မရဘူး။ အစပိုင်းဒေတာထည့်တဲ့
  လုပ်ငန်းစဉ်ကဖြစ်စေ၊ တခြား`စနစ်အုပ်ချုပ်သူ`ကဖြစ်စေ ဖန်တီးပေးရမယ်
- ကိုယ့်အကောင့်စာမျက်နှာကနေ ကိုယ့်အခန်းကဏ္ဍကို ပြောင်းလို့မရဘူး
- အသစ်ဖန်တီးထားတဲ့ အခန်းကဏ္ဍကို လုပ်ပိုင်ခွင့်မသတ်မှတ်ရသေးရင်
  ဘာမှလုပ်ခွင့် မရဘူး
- အခန်းကဏ္ဍကုဒ်ကို ဖန်တီးပြီးရင် အမည်ပြောင်းလို့မရဘူး
- အများသုံးလမ်းကြောင်းတွေကို တိုကင်မပါဘဲ အသုံးပြုလို့ရမယ်
- အများသုံးမဟုတ်တဲ့ လမ်းကြောင်းအားလုံးမှာ မှန်ကန်တဲ့ Bearer access token
  မပါရင် ငြင်းပယ်ရမယ်

## ၉။ ဘယ်အခြေအနေကို အောင်မြင်တယ်လို့ သတ်မှတ်မလဲ

အောက်ပါအချက်တွေအားလုံး ပြည့်မီရင် ဒီကဏ္ဍ အောင်မြင်တယ်လို့ သတ်မှတ်ပါမယ် —

- `ဖောက်သည်` သို့မဟုတ် `ရောင်းချသူ`အဖြစ် အကောင့်ဖွင့်နိုင်တယ်
- `ဖောက်သည်`က အကောင့်ဖွင့်ပြီးတာနဲ့ စနစ်ဝင်နိုင်ပြီး `JWT` တိုကင်ရတယ်
- `ရောင်းချသူ`က `PENDING_APPROVAL` အခြေအနေကို ရပြီး `စနစ်အုပ်ချုပ်သူ`
  အတည်ပြုမချင်း စနစ်ဝင်လို့မရဘူး
- `စနစ်အုပ်ချုပ်သူ`က `ရောင်းချသူ`အကောင့်ကို အတည်ပြု၊ ငြင်းပယ်၊ ယာယီပိတ်နိုင်တယ်
- အများသုံးမဟုတ်တဲ့ လမ်းကြောင်းကို စနစ်မဝင်ဘဲ ခေါ်ရင် 401 ပြန်တယ်
- စနစ်ဝင်ထားပေမယ့် လုပ်ပိုင်ခွင့်မရှိတဲ့အလုပ်ကို လုပ်ရင် 403 ပြန်တယ်
- ဆိုင်မျက်နှာစာက ကုန်ပစ္စည်းတွေကို စနစ်မဝင်ဘဲ ကြည့်နိုင်တယ်
- ကုန်လက်ကျန်ဆိုင်ရာ controller တွေက `X-Actor-Id` header ကို
  မယုံကြည်တော့ဘူး
- နောင်မှာ ပြင်ပ IdP ကို ပြောင်းသုံးတဲ့အခါ အသုံးပြုသူကို ကိုယ်စားပြုတဲ့ပုံစံ၊
  စနစ်ရဲ့ လုပ်ပိုင်ခွင့်စစ်ဆေးပုံနဲ့ ပိုင်ဆိုင်မှုစစ်ဆေးပုံတွေ မပြောင်းဘဲ
  စကားဝှက်နဲ့ တိုကင်ပိုင်းကိုပဲ အစားထိုးနိုင်တယ်
- အမှားအဖြေတွေက လက်ရှိ `ProblemDetail` ပုံစံအတိုင်း ဖြစ်တယ်

## ၁၀။ နောင်မှာ ပြင်ပအသုံးပြုသူစိစစ်ရေးဝန်ဆောင်မှုနဲ့ ဘယ်လိုချိတ်မလဲ

- ပြင်ပဝန်ဆောင်မှုကို ပြောင်းသုံးပြီးရင်တောင် ဒီစနစ်ထဲက platform user ID ကို
  ဆက်ထိန်းထားရမယ်
- ပြင်ပအကောင့်နဲ့ ဒီစနစ်ထဲကအကောင့်ကို အီးမေးလ်နဲ့ မချိတ်ရဘူး။
  ပြင်ပဝန်ဆောင်မှုကပေးတဲ့ `(issuer, subject)` အတွဲနဲ့ပဲ ချိတ်ရမယ်
- စကားဝှက်၊ စနစ်ဝင်ခြင်းနဲ့ တိုကင်သက်တမ်းကို ပြင်ပဝန်ဆောင်မှုက တာဝန်ယူမယ်။
  `ရောင်းချသူ`အတည်ပြုခြင်း၊ အကောင့်ယာယီပိတ်ခြင်း၊ အခန်းကဏ္ဍ၊ လုပ်ပိုင်ခွင့်နဲ့
  ပစ္စည်းပိုင်ဆိုင်မှုတို့ကိုတော့ ဒီစနစ်ကပဲ ဆုံးဖြတ်မယ်
- Keycloak realm role၊ client role၊ group၊ scope သို့မဟုတ်
  introspection field တွေကို ဒီစနစ်ရဲ့ အခန်းကဏ္ဍတွေနဲ့ ချိတ်နိုင်ရမယ်။
  ပြင်ပဝန်ဆောင်မှုနဲ့ သက်ဆိုင်တဲ့ အချက်အလက်အစစ်တွေကို controller တွေအထိ
  မပို့ရဘူး
- `AccessTokenAuthenticator` က ကိုယ်တိုင်ထုတ်ထားတဲ့ `JWT`၊ discovery နဲ့
  `JWKS` သုံးပြီး စစ်ထားတဲ့ ပြင်ပ `OIDC/OAuth2 JWT`၊ introspection သုံးပြီး
  စစ်ထားတဲ့ opaque token အားလုံးကို `ExternalPrincipal` ပုံစံတစ်မျိုးတည်း
  ဖြစ်အောင် ပြောင်းပေးရမယ်
- `PlatformIdentityResolver` က `ExternalPrincipal` ကို controller နဲ့
  handler တွေသုံးမယ့် `AuthenticatedActor` အဖြစ် ပြောင်းပေးရမယ်
- မူရင်း `JWT` claim၊ introspection အဖြေ သို့မဟုတ် provider SDK အမျိုးအစားကို
  framework နဲ့ လုပ်ငန်းကုဒ်တွေဆီ မပို့ရဘူး
- ကာကွယ်ထားတဲ့ API တွေက `OAuth2 access token` ကိုပဲ လက်ခံရမယ်။
  `OIDC ID token` ကို API ဝင်ခွင့်တိုကင်အဖြစ် လက်မခံရဘူး

## ၁၁။ ဘာတွေကို မှီခိုထားလဲ

ဒီကဏ္ဍက အောက်ပါအစိတ်အပိုင်းတွေကို သုံးထားပါတယ် —

- framework ကဏ္ဍထဲက `AggregateRoot`၊ `Id`၊ `ErrorCategory` နဲ့ CQRS bus
- အမှားအဖြေပုံစံ တစ်သမတ်တည်းဖြစ်ဖို့ `GlobalApiExceptionHandler`
- အသုံးပြုသူအချက်အလက် သိမ်းဖို့ PostgreSQL
- Bearer တိုကင်ကို လက်ခံစစ်ဆေးတာ၊ `JWT` စစ်တာ၊ opaque token ကို
  introspection လုပ်တာနဲ့ လုပ်ပိုင်ခွင့်စစ်တာတွေအတွက် Spring Security ရဲ့
  `OAuth2 resource-server` ပံ့ပိုးမှု
