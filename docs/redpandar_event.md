# Redpanda integration events for standalone services

**Implementation plan · 18 November 2026**

After extraction from the Modulith, Account, Merchandising, Channel, Checkout, and Workflow will use a shared Redpanda broker for public integration events. Each service will publish from its own PostgreSQL outboxes and apply incoming events through its own transaction managers and CQRS buses. The first release gate is a Catalog write in one process producing a queryable Discovery projection in another.

The rollout uses one topic per producing service and a coordinated production handover from the monolith. Synchronous Java/RMI ports continue to serve commands and queries. Workflow participates in the infrastructure rollout with its existing signal port and local dispatch path. Moving participant execution to broker messages is a separate migration.

Each entry MUST identify the producer context, contract and version, aggregate key, subscribing services, logical consumer keys, and destination transaction managers. A service subscribes to its own topic when it handles one of its public events. Replicas of that service share one consumer group.

## 3. Wire contract and processing rules

| Record element | V1 convention |
| --- | --- |
| Topic and consumer group | `grab.<owner>.events.v1` and `grab.<consuming-service>.events.v1`. An example subscription is group `grab.channel.events.v1` reading `grab.merchandising.events.v1`. |
| Key | Encode source context, aggregate type, and aggregate ID as an unambiguous UTF-8 tuple. Use compact JSON array encoding. The pilot key is `["catalog","ProductVariant","<variant-id>"]`. |
| Identity and time | `event-id` is the persisted integration-outbox UUID. `occurred-at` is the original outbox timestamp in UTC. Preserve the business occurrence time and any publication ID already present in the contract body. Carry `trace-id` when available. |
| Type and body | Use a stable logical `event-type`, integer `schema-version`, and `content-type=application/json`. For the pilot use `merchandising.catalog.product-published-to-channel`, version 1. Its JSON body contains `variantId`, `salesChannelId`, `occurredAt`, and `version`. [Pilot contract](../service/marchendising/merchandising-event-contract/src/main/java/com/grab/service/contract/event/merchandising/catalog/ProductPublishedToChannelIntegrationEvent.java) |
| Compatibility | Register each supported logical name and version against a concrete record class at assembly time. Readers tolerate additive optional fields. Deploy readers for a new version before enabling its writers. Resolve historic `com.grab.app.shared.events.*` aliases during **outbox deserialization**, before the relay calls the dispatcher. Decode broker input using the explicit registry. Exercise legacy JSON fixtures in a standalone classpath. |

**Producer.** Keep local Spring notifications for private domain transitions, lifecycle hooks, and synchronous translation inside an owner transaction. Write the integration record to that owner’s outbox in the same transaction as the change. Where translation itself consumes a previously committed domain outbox row, persist a translator receipt and the new integration row in one owner transaction. This prevents a retried parent event from minting multiple output UUIDs. Distinguish these paths when auditing the existing `*InProcessDomainEventPublisher` beans.

For public records, send only to the owning topic. Enable producer idempotence and `acks=all`. Bound the send wait and configure the full producer blocking and delivery budget below the outbox claim timeout. On an ambiguous result retain the same event UUID for the retry. An unavailable broker must never trigger a successful local fallback. [Redpanda idempotent producers](https://docs.redpanda.com/streaming/current/develop/produce-data/idempotent-producers/)

**Consumer.** Disable automatic offset commits. Read raw bytes, validate the envelope, and check the topic owner against the catalogue. Acknowledge a known event outside the service’s subscriptions without loading its payload class. Quarantine malformed envelopes, unrecognised types, and unsupported versions of subscribed types. Bind the original UUID, dispatch metadata, and trace around synchronous Spring delivery, then restore the previous context in all outcomes. The ingress adapter MUST NOT pass incoming records to the outbound dispatcher.

Each interested listener commits its receipt, business change, and resulting outbox writes together under its own transaction manager. Acknowledge the Kafka record after all interested listeners return successfully. If listener A commits and listener B fails, redelivery skips A through its receipt and retries B. Maintain separate receipt keys for separate effects even when one service group consumes both. [Existing inbox listener](../outbox-infrastructure/src/main/java/com/grab/outbox/infrastructure/inbox/AbstractIntegrationEventListener.java)

**Ordering.** The key keeps records for one aggregate on one partition. Concurrent outbox workers, retries, and dead-letter replay can still deliver an older source change after a newer one. Discovery should reconcile current facts through its published query ports. For projections that apply snapshots directly, carry an authoritative source revision and persist the last applied revision in the projection transaction. For order-sensitive cascades, test delete/restore and suspend/reactivate sequences with delayed delivery before activating the route. Schema version is a contract property and cannot serve as an aggregate revision.

## 5. Operations, replay, and production handover

- **Provisioning.** Use one broker and replication factor one in local Compose. Production uses a replicated cluster with topic replication factor three. Provision owner topics and active source/consumer dead-letter topics before enabling publishers. Grant each service writes to its owner topic, reads on subscribed topics, access to its own group, and writes to its dead-letter destinations. Use deployment-managed credentials. [Redpanda topic configuration](https://docs.redpanda.com/streaming/current/develop/manage-topics/config-topics/)
- **Retries.** After the first failed attempt, retry a transient consumer failure three times at two-second intervals. Send exhausted or invalid records to `<source-topic>.<consuming-service>.dlt`. Preserve the original bytes, key, headers, source partition/offset, failed group, and error classification. Commit the source offset only after an acknowledged dead-letter write. If that write fails, keep the offset pending. [Spring Kafka error handling](https://docs.spring.io/spring-kafka/reference/kafka/annotation-error-handling.html)
- **Replay.** Use a seven-day automatic delivery and operator replay window measured from the immutable original outbox timestamp. Retain receipts for at least 14 days and provision topic retention to cover the replay window. Apply the age check at source replay, ingress, and dead-letter redrive. After correcting the failure, an operator may republish an eligible record with its original key, UUID, timestamp, and contract version. Already successful consumers skip it. Reconcile expired records against authoritative service state and record the corrective action. Preserve malformed records lacking usable identity for investigation.
- **Monitoring.** Expose oldest pending outbox age, retry/dead counts, producer errors and latency, consumer lag and its age, duplicate receipts, dead-letter depth, and last successful receipt by critical route. Alert on sustained lag, dead-letter arrival, and backlog approaching the replay horizon. Use bounded service/topic labels and put event IDs in structured logs. Headless service startup must complete during broker outages. Report transport health independently from process liveness. [Existing outbox metrics](outbox-observability.md)

**Production cutover**

1. Deploy compatible consumers, validate topics and ACLs, and record initial offsets while standalone writers and competing outbox relays are disabled. Confirm that each service can decode a representative legacy record and that the target databases contain the expected business state and inbox history.
2. Pause monolith writes, scheduled publishers, and bootstrap producers. Let the active monolith finish its outstanding deliveries, including downstream outbox rows created while draining. Capture per-outbox counts and UUIDs for failed, dead, and in-flight rows. Reconcile outstanding failures before handover.
3. Stop the monolith relays, including hot-queue workers. Complete the final database transfer if ownership moves across databases. Preserve event UUIDs, outbox status, receipt keys, and workflow signal receipts. Assign exactly one runtime deployment per outbox and record its ownership and offsets.
4. Start standalone consumers and relays. Verify partitions are assigned, manifests reach Identity, the Catalog pilot updates Discovery, and Account approval provisions a Channel website. Reopen traffic when the checks pass and lag is draining within the replay window.
5. Before standalone mutations, rollback may restore the former owner after stopping the new relays. Once standalone services commit changes, pause writes, account for broker offsets and downstream effects, and reconcile database state before reversing ownership. Prefer a forward repair when the new services already own committed work. A configuration toggle alone cannot recover that state.

## 6. Acceptance suite

Use PostgreSQL and Redpanda Testcontainers for transaction and transport tests. Run the pilot smoke test in separate JVMs on Compose. The following checks are release criteria for the implementation. [Redpanda Testcontainers](https://java.testcontainers.org/modules/redpanda/)

| Test | Observable pass condition |
| --- | --- |
| Normal write and rollback | A committed publication reaches the Discovery query. Rolling back the Catalog transaction leaves no committed integration row, broker message, or Discovery effect. |
| Producer crash windows | With Redpanda unavailable, a committed integration row remains recoverable by the outbox. A crash after broker acknowledgement and before marking published can produce duplicate records carrying the same UUID and one committed consumer effect. |
| Consumer crash and partial fan-out | A crash after destination commit and before offset commit skips the completed effect on restart. When a second listener fails, the first listener’s committed effect stays singular and the second eventually succeeds. |
| Translation and concurrent delivery | Retrying a durable domain-to-integration translator produces one integration row per intended output. Two contenders for the same logical receipt produce one committed receipt and effect. |
| Contract and routing | Exercise each supported legacy alias, concrete manifest type, additive field, unsupported subscribed version, malformed JSON, and known unsubscribed type. Public events use one outbound path, and private events stay inside their owning service. |
| Ordering and recovery | Deliver an older update after a newer update, exercise consumer rebalance, fail the dead-letter publish, and redrive a repaired record. Check final business state, preserved UUID, and offset position at each failure. Expired replay enters reconciliation. |
| Service boundaries | Start all five services in both transport modes. Run ArchUnit checks for headless services, group-scoped buses, schema ownership, and Kafka dependencies confined to transport/assembly. Verify Workflow signal idempotency and Cart local event delivery. |

From the repository root, the implementation verification should include the affected Maven reactor and the separate-process smoke test. The overlay filename below is a planned deliverable.

```sh
./mvnw -pl :redpanda-adapter,:account-service,:merchandising-service,:channel-service,:checkout-service,:workflow-service -am verify
docker compose -f docker-compose.yml -f docker-compose.redpanda.yml --profile workflow config --quiet
```
